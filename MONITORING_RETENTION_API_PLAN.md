# План: ретеншен мониторинга и программный доступ к API

Аудит от 24.08 по двум вопросам: (1) чистится ли мониторинговая БД на сателлите,
(2) можно ли дотянуться до данных мониторинга через API без браузера. Сначала — что
проверено и что подтвердилось, дальше план по каждому.

---

## 1. Ретеншен: проблема реальная, но уже наполовину решённая

### Что есть на самом деле

Проверено на живой базе (`show create table` по всем таблицам):

| Таблица | TTL | Кто пишет | Кто читает |
| --- | --- | --- | --- |
| `inference_events` | **30d** | коллектор (pipeline events) | Query API, воркер |
| `monitoring_results` | **30d** | воркер | Query API |
| `monitoring_alerts` | **30d** | воркер | Query API |
| `monitoring_worker_failures` | **30d** | воркер | Query API |
| `otel_traces` | **нет** | коллектор (pipeline traces) | Query API (дерево спанов) |
| `inference_requests` | **нет** | коллектор (pipeline metrics) | **никто** |
| `inference_errors` | **нет** | коллектор (pipeline metrics) | **никто** |
| `inference_latency_ms_bucket/count/sum` | **нет** | коллектор (pipeline metrics) | **никто** |

То есть ретеншен-механика существует и работает — но покрывает только четыре таблицы,
которые создаёт сам стор. Пять таблиц, которые создаёт **коллектор**, растут вечно.

Два отягчающих факта:

- **Докстринг врёт.** `greptime.py::_ensure_tables` обещает «The TTL is applied … including
  to the traces table the collector owns», и в `MONITORING_FIXES.md` записано то же самое —
  но вызова `_apply_ttl(OTEL_TRACES_TABLE, …)` в коде нет. Судя по всему, строка потерялась
  при рибейзе. Это не «не сделали», это «сделали и потеряли», что хуже: все считали вопрос
  закрытым (в `MONITORING_GAPS.md` Open Question 3 помечен решённым).
- **Самая быстрорастущая таблица — мёртвый груз.** `inference_latency_ms_bucket` — 160 тыс.
  строк после пары дней демо-трафика (для сравнения: `inference_events` — 4.4 тыс.).
  Метрики экспортируются периодически, по строке на серию на бакет гистограммы, и их
  **никто не читает**: рантайм-серии дашборд считает из сырых событий. Проверено grep'ом —
  ни одного чтения этих таблиц в коде агента.

Что НЕ подтвердилось: сырые входы-выходы моделей в непокрытых таблицах не лежат. Коллектор
фильтрует событийные спаны в `inference_events` (покрыт TTL), в `otel_traces` попадают
только обычные спаны `inference` / `model.execute` без payload'ов. То есть непокрытые
таблицы — проблема роста диска, а не удержания чувствительных данных.

### План (полдня)

1. **Достроить `_ensure_tables`**: применять TTL к таблицам коллектора тем же
   `_apply_ttl`-циклом — `otel_traces` (новая настройка `MONITORING_TRACES_TTL`, дефолт
   30d, как у событий: вкладка Traces смотрит на тот же горизонт) и четыре таблицы метрик
   (`MONITORING_METRICS_TTL`, дефолт 7d — их никто не читает, храним коротко на случай
   будущих нужд). `_apply_ttl` уже терпит отсутствующую таблицу, так что первый старт до
   появления трафика ничего не ломает.
2. **Починить докстринг** — чтобы обещал ровно то, что делает.
3. **Тесты**: расширить `tests/monitoring/test_retention.py` — TTL применяется ко всем
   девяти таблицам, отсутствующая таблица пропускается без ошибки.
4. **Проверка вживую**: после пересборки `show create table` по всем таблицам должен
   показать TTL везде.

Решения, которые предлагаю принять сейчас и записать:

- ~~Метрик-pipeline оставить, но с коротким TTL~~ **Решено иначе (24.08): экспорт метрик
  выключен.** Аргумент «может пригодиться» не выдержал проверки: горизонт событий (30d)
  покрывает любое окно дашборда, то есть не существует вопроса, на который метрики
  отвечают, а события — нет. При этом периодический экспортер переписывал каждую серию
  раз в минуту независимо от трафика — стоимость росла с аптаймом, а не с нагрузкой.
  Выключено с обеих сторон: у коллектора убран pipeline metrics, у агента метер стал
  no-op (запись в `InferenceMetrics` осталась — инструментация не тронута, экспортер
  возвращается одной правкой). TTL 7d на таблицах метрик остаётся, чтобы накопленное на
  работающих стендах стекло само.

  **Сверка со спекой (24.08, по вопросу «а не заготовка ли это»).** Заготовка — да:
  спека числит `runtime_metrics` датасетом Local Storage Model (строка 321), входом
  Runtime Health (строка 435) и поставкой фазы 1 (строка 867); OTel-экспорт появился в
  `9cba092b` (feat/satellite-instrumentation, фаза 1) как реализация этого пункта. Но
  позже (`35c11093`, feat/monitoring metrics processing) воркер начал материализовывать
  **те же агрегаты** — request/success/error count, error_rate, latency p50/p95/max,
  timeout и failed count по 5-минутным окнам на деплой — в `monitoring_results`, и именно
  их дашборд читает (история метрики в детали алерта). Роль спекового `runtime_metrics`
  в этой реализации несёт `monitoring_results`; OTel-таблицы — первый слой, вытесненный
  вторым, который забыли выключить.

  **Длинный горизонт («сравнить показатели за большой период»)** — этот сценарий закрыт
  той же таблицей: захотим сравнивать дольше 30 дней или укоротить сырые события — надо
  поднять `MONITORING_RESULTS_TTL`. Окна результатов лёгкие (несколько метрик на окно
  против ~15 бакетов × серию × минуту у OTel), без сырого IO, уже по-деплойные и уже
  читаются кодом; кумулятивные поминутные счётчики для этого хуже по всем пунктам. Если
  когда-нибудь понадобится внешний потребитель именно OTel-метрик (Grafana поверх
  Greptime и т.п.) — вернуть экспорт: правка одной строки в `telemetry.py` (экспортер
  обратно в метер) плюс pipeline `metrics` в конфиге коллектора; при возврате сразу
  ставить интервал экспорта ≥300 сек.
- **Данные удалённых деплоев** доживают до TTL, отдельной чистки при undeploy нет. Для
  30-дневного горизонта это приемлемо; если станет проблемой — воркер уже умеет ходить в
  базу, чистка по списку живых деплоев добавляется в его тик. Сейчас не делаем.

## 2. Программный доступ: проблема в авторизации, не в покрытии

### Что есть на самом деле

Сами данные через API уже доступны почти целиком — Query API отдаёт header, overview,
runtime, data-quality, feature-drift, reference-profile, alerts, traces, worker health.
«Дотянуться» есть до чего. Проблема ровно в том, как к этому пускают:

- единственный вход — **одноразовый** launch-token (5 минут), который минтит платформа
  по браузерному сценарию;
- он обменивается на **cookie-сессию**: 30 минут, без продления, живёт в памяти агента
  (умирает при рестарте), привязана к **одному** деплою;
- write-зависимость (`require_monitoring_write` для acknowledge) — сегодня та же сессия.

Скрипту приходится изображать браузер: наши же генераторы трафика делают ровно этот танец
(POST launch-token → редирект → выковырять cookie). Работает, но это обход, а не интерфейс:
на N деплоев нужно N токенов и N сессий, рестарт агента всё сбрасывает, а cookie в
не-браузерном клиенте — вечный источник боли.

Вывод: **согласен**. Дизайн launch-token правильный для iframe (спека прямо запрещает
дашборду зависеть от долгоживущих ключей), но машинного пути он не заменяет — спека,
кстати, сама упоминает «target-ingestion credential» как отдельную сущность для приёма
таргетов, то есть машинный credential в архитектуре предполагался.

### Ключевое наблюдение, которое упрощает задачу

У агента **уже есть** машинная авторизация с нужной семантикой: инференс принимает
`Bearer <LUML API key>` и проверяет его интроспекцией у платформы
(`/satellites/v1/deployments/inference-access`, кэш 60 сек). А проверка прав на платформе
там — `Resource.DEPLOYMENT, Action.READ` на орбите сателлита — **та же самая**, которой
гейтится выдача monitoring launch-token. То есть «ключ, которому можно звать инференс,
может и читать мониторинг» — не расширение прав, а ровно та же привилегия.

Второе наблюдение — почему «сам механизм не подходит», структурно: у Query API **деплой
зашит в сессию, а не в URL** (`/monitoring/api/overview`, без id — id берётся из cookie).
Пока это так, ключевая авторизация не приделывается в принципе: ключ орбитный, а маршрут
без адресата. Это и есть главная переделка.

### План (1–2 дня)

**Шаг 1 — деплой в путь.** Новые маршруты
`/monitoring/api/deployments/{deployment_id}/…` для всех секций, тем же
`MonitoringQueryService` (он и так принимает `deployment_id` первым аргументом — правка
только в роутере). Сессионный вызов обязан совпадать с `session.deployment_id`, иначе 403.
Старые бес-id маршруты остаются для дашборда как тонкие обёртки — iframe не трогаем.

**Шаг 2 — Bearer-ветка авторизации.** Зависимость `require_monitoring_access`: либо
валидная cookie-сессия (как сейчас), либо `Authorization: Bearer dfs_…`, проверенный через
существующий `authorize_inference_access` с его 60-секундным кэшем. Ключевая ветка
работает только на маршрутах с явным `deployment_id`. Write-операции (acknowledge) в v1
оставляем сессионными — ключ читает, человек подтверждает; ослабить можно потом одной
правкой, зависимость уже выделена.

**Шаг 3 — перечисление.** `GET /monitoring/api/deployments` (только Bearer): какие деплои
на этом сателлите мониторятся, их id и статус — чтобы машинному клиенту было с чего
начать, а не таскать id с платформы.

**Шаг 4 — потребители.** Перевести генераторы из `dfs_test` с launch-token-танца на ключ —
это заодно живой прогон нового пути. Задокументировать в README сателлита.

**Шаг 5 (опционально, отдельно) — платформенная сторона.** Сейчас переиспользуем
inference-интроспекцию, потому что права совпадают. Если позже захотим отдельный скоуп
`monitoring:read` для ключей (ключ «только мониторинг», без инференса) — это новый
интроспекшн-эндпоинт на платформе; закладываться сейчас не надо, интерфейс агента от
этого не изменится.

Что сознательно НЕ делаем: не даём ключам минтить launch-token'ы пачками (усугубляет
обход), не переносим мониторинговые данные на платформу (спека это прямо запрещает), не
трогаем iframe-путь.
